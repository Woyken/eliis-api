## Finding 1 — rejection-only `message` is folded into both default response bodies

**Major; blocks a clean auth/discovery review.** `models/responses.tsp` declares `message?: unknown` in `LoginResponseBody` (lines 1778–1787) and `Login2FAResponseBody` (1797–1804), and each model is returned as its operation's `@defaultResponse` (`LoginStaticResponse` / `Login2FAStaticResponse`). The evidence text correctly says that `message` is read only from `error.response.data.message`, but placing it alongside successful-fulfillment observations in the same default body still combines distinct branches in the modeled response shape. Optionality prevents a requiredness claim; it does not make this a fulfillment-body observation.

Original source confirms the branch distinction: password login handler `#13517` first guards `error.response`, `response.data`, and truthy `message` before displaying it (`eliis.hasm` 543815–543844); the 2FA rejection handler `#27145` does the same (`1048494–1048524`). By contrast, successful login handling reads `response.data.type` and passes that data object to the 2FA screen (`#13510`, 543554–543652), while successful 2FA projects `response.data` (`#16310`) and its caller reads `status` / branch-local `locked_at` (`#27143`, 1048399–1048423).

**Correction requested:** keep each success-path partial body limited to its fulfillment observations (`Login`: `type`, `identifier`, `locked_out`; `Login2FA`: `status`, `locked_at`). Preserve the rejection-only `message` read separately as a non-normative client response observation or explicitly separated error-branch evidence; do not invent an HTTP error status, universal error wrapper, or success/error schema union. The capability prose already makes the rejection distinction and should continue to do so.

## Remaining boundaries confirmed (not findings)

- Login UI comparisons against Axios `response.status` 200/202 and default-client interceptor branches 401/412/429 are client branches, not universal status contracts. The successful auth response cookie effect is header-driven and distinct from body properties. No expired-session meaning is established.
- Init `guardians[*].kindergarten_id` is only used for a client-side kindergarten match; no guardian ID, child join, or authorization proof appears. Init `children[*].id` is used by the picker but has no traced causal handoff into downstream route `childId`.
- Profile caller context is local state routing only. The `active_courses` mutation/wrapper does not imply an HTTP write or add a `course` body property.
- Course item IDs are reused locally and for a separate `course_id` GET; no stable ID or institution-enrollment guarantee follows.
- The eight permission keys are a partial selector inventory, not typed Boolean fields or a server policy contract.
