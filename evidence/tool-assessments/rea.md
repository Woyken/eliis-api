# REA fit assessment for the Eliis HBC/API evidence workflow

**Verdict: useful only as a conditional side tool; not a Hermes bytecode or API-response evidence analyzer.** REA could help inspect ordinary JavaScript modules if readable source is separately available, and could provide supplemental Android Java/Smali inspection with its specific JADX MCP engine. Neither path replaces tracing the existing Hermes v96 disassembly (`.hasm`) or the project's required service → caller/action → reducer/consumer evidence chain. Do not install or configure REA for the current task on the evidence reviewed here.

## Scope and upstream revision

This assessment used public REA documentation, package metadata, GitHub source listings, and release metadata only. No Eliis APK, local captures, credentials, or private responses were opened or sent to REA.

- Repository `main` at review time: [`0fa0b046288bc1b70099a2d27ee52537850de595`](https://github.com/morluto/rea/tree/0fa0b046288bc1b70099a2d27ee52537850de595) (2026-10-10).
- Latest published npm version reported by REA's release-boundary documentation: [`rea-agents@6.3.0`](https://github.com/morluto/rea/releases/tag/rea-agents-6.3.0), published from [`74cf9e1401fcd89482fe39c27cc898f5858e9b72`](https://github.com/morluto/rea/tree/74cf9e1401fcd89482fe39c27cc898f5858e9b72). The release notes/docs say the published package includes Android/JADX tools.
- There is a documentation inconsistency: [`docs/android-analysis.md`](https://github.com/morluto/rea/blob/0fa0b046288bc1b70099a2d27ee52537850de595/docs/android-analysis.md) says the feature is in npm `4.1.0`, while [`docs/installation.md`](https://github.com/morluto/rea/blob/0fa0b046288bc1b70099a2d27ee52537850de595/docs/installation.md#released-package-and-main) says `6.3.0` includes Android/JADX. The release-boundary document and release commit are the more recent, specific package evidence; verify a connected server's tool list before relying on it. `main` is newer than the published commit, so main-only changes must not be assumed to ship in 6.3.0.

## Hermes-name disambiguation

REA's `src/application/HermesClientHome.ts` ([main source](https://github.com/morluto/rea/blob/0fa0b046288bc1b70099a2d27ee52537850de595/src/application/HermesClientHome.ts)) is filesystem/profile resolution for the **Hermes coding-agent client**: it interprets `HERMES_HOME`, `HERMES_DATA_DIR_SUFFIX`, and sticky profiles. The installation guide's Hermes sections and `verify:hermes-client` package script are agent registration/client-integration features. They are not Hermes VM, HBC, or React Native bytecode support. I found no public REA parser/decoder operation or documented HBC input path. This is based on the reviewed public package/docs/source listings, not a claim that no future or unlisted third-party extension could exist.

## Host and version fit

- `package.json` on main declares Node `^22.19.0 || ^24.11.0 || >=26.0.0`; Node **24.15** is within the declared Node range. The package also expects npm. This declaration does not itself promise every provider's architecture/platform behavior.
- Static JS reconstruction is documented without a native engine, but the documentation does not explicitly verify the exact Ubuntu/proot/aarch64 combination. Treat generic Node compatibility as plausible, not provider validation.
- Android/JADX documents a full JDK 17+ (including `jdk.compiler`) and a caller-supplied `jadx-headless-mcp-0.7.1-all.jar`. The workspace's Java 21 meets the Java-version minimum **if it is a full JDK**. Docs explicitly say the POSIX adapter supports Linux, but cite a real bridge verification on macOS arm64 and do not assert Linux/aarch64 as a tested combination. Linux JDK 25 is separately called out as not yet real-verified; this workspace has JDK 21, not JDK 25.
- The locally noted JADX 1.5.6 installation is **not documented as a drop-in substitute** for REA's required `jadx-headless-mcp` 0.7.1 protocol JAR. REA checks for bridge classes and protocol-compatible engine material. Do not point `REA_JADX_MCP_JAR` at an arbitrary JADX JAR and assume compatibility.
- Ghidra's provider does explicitly document Linux arm64, with Ghidra 12.1.x and its required full JDK; the platform-native decompiler must match. The docs do not specifically validate this Android/proot host. Hopper is not needed for Android/JADX or static JS.

## Recommendation / cost boundary

1. **Do not use REA on `.hbc` or `.hasm` for this audit.** No supported bytecode path was evidenced; the existing Hermes v96 disassembly remains the primary source.
2. **No network-capture experiment.** Do not supply raw/private captures. If a later task authorizes a capture workflow, first produce a separate sanitized HAR with secrets removed and confirm that it contains no private response/identity data; custom project JSON should stay in its existing local analysis path.
3. **Possible low-cost, separate Java adjunct:** only if a compatible REA CLI and the exact `jadx-headless-mcp 0.7.1` JAR are already available, an operator could run a small inspection against the public ApiDemos fixture or a specifically approved target APK. This is optional and should answer only a Java-wrapper question. It needs no Android SDK/emulator, but the JAR is an additional prerequisite, Linux/aarch64 isn't explicitly proven, and the result won't provide HBC callsites or exact DEX offsets. No download, install, npm command, setup, or local test was performed for this review.
4. **Conditional JS follow-up:** if an independently recovered, genuine UTF-8 JS bundle/module set becomes available, REA's source-only graph may be worth a bounded read-only trial on those files. The current Hermes bytecode artifact does not satisfy that input requirement.
5. **Ghidra is deferred:** use only for a distinct native `.so` question after confirming an existing supported Ghidra/JDK/native-decompiler setup. It is not a workaround for missing Hermes-bytecode parsing.
