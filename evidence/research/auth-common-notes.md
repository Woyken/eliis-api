# Auth/common bytecode research notes

Source blocks: `/data/data/com.termux/files/home/eliis-analysis/domain-source/auth-common.hasm`; function IDs and original full-disassembly line numbers are recorded on each operation in `auth-common.json`. Records cover all 41 assigned functions.

## Authentication/client evidence

- Function #16308 (`login`) invokes `auth.post(url, data)`, while the other assigned request functions invoke `default` Axios. #5603 (full lines 254019–254130) +0x13e/+0x143 creates/exports the separate `auth` instance; +0x153/+0x158 creates/stores default. Only default receives the configured cookie-attaching request interceptor (+0x169–+0x189). Both have response interception: default +0x19c–+0x1b8 and auth +0x1be–+0x1da. Auth's #5621 +0x03/+0x0c invokes environment slot 8, the shared setCookie helper installed at #5603 +0x18f–+0x198. #5615 +0x10–+0x1e wraps #5616, which creates #5617 at +0x02; #5618 +0x05–+0x15 forwards to the captured helper. #5617 (full lines 254464–254517) +0x0d–+0x36 parses `headers['set-cookie'][0]`, +0x3b–+0x58 extracts/serializes `eliis_csrf`, and +0x91/+0x97 saves it using `saveAccessToken`. Thus Login remains `auth: none` and the other 40 operations remain `cookie`: these are configured request-client classifications, not claims of server requiredness, absent native cookies, or inability to capture a login response cookie. No Bearer scheme is established.

## Helper-level boundaries and later callsite evidence

- The service wrappers forward arbitrary arguments for registration, verification/recovery, profile update, 2FA enable/password verification, and similar calls. Where later caller constructors establish named fields, the final records retain open partial models and `clientRequestVariants`; this does not close the service's arbitrary input or establish all callers. The separate request-model enrichment records and reviews identify those constructor chains.
- Functions #16309, #16311, and #16314 mutate caller-provided objects before posting (the two social calls also supply `app_login: true` in `config.params`). At the service-mutation layer, Login2FA assigns outer `platform`; each social call assigns outer `platform`, `role`, `tz`, `lang`. Additional Login2FA `code`/`login_identifier` fields come from a separately reviewed caller, not these mutations. Arbitrary forwarded remainder stays unknown/open; no outer `login` or assigned outer `social` is inferred from the services. Social +0x24/+0x28/+0x2e mutates the constructor result's nested `login=input.social`, +0x34 assigns `input.platform`, and +0x3a–+0x52 assigns outer `role=null`, `tz=-180`, `lang="en"`. Field `value` records a client assignment only, not server enums/defaults/nullability/requiredness.
- Function #16361 forwards caller multipart POST data. The bounded final caller trace #40854 → shared #40894/#40898 → #16229/#16230 → installed #16361 proves literal `profile_picture` in the named EditUserProfileImage variant. Its file value remains unknown; native `name/type/uri` descriptor members are transport metadata, not API properties. The endpoint model stays partial (`complete:false`).
- Function #26882 supplies its argument as `axios.get(url, config)`, not as a params object. Its arbitrary Axios config shape is unresolved, so it is documented in notes rather than fabricated as named query fields.
- #16340 `getPlatform` (full lines 649231–649258, absolute 0x004f5894) constructs exactly two fresh own fields: string `platform` at +0x05–+0x39 (`systemName + " " + systemVersion + ", Model: " + model + ", Device id: " + deviceId`) and string `browser` at +0x3e–+0x59 (`"Mobile app v" + getVersion()`). #16339 +0x58–+0x9b traces environment slots 1–4 to getDeviceId/getModel/getSystemName/getSystemVersion; +0x9f/+0xa4 exports #16340. All six consumers preserve this construction as nested `fields` metadata. Object-valued field types remain `unknown` within the existing vocabulary, not wholly unknown construction.
- Login #16308 +0x22–+0x2a assigns nested `login="password"`, and +0x40–+0x58 constructs exactly three outer fields `username`, `password`, `platform`. Logout #16323 +0x21–+0x29 makes the same nested assignment, then +0x41/+0x46 supplies the object as `config.params.platform` without local JSON.stringify. The observed nested string constant is not a server enum.
- Logout's default query serialization is separately traced: #5683 +0x74–+0x97 constructs AxiosURLSearchParams; #5681 +0x1e invokes #5669 toFormData, whose +0x9e sets dots=false; #5674/#5677 recursively walk the object and #5666/#5667 render bracketed keys. No custom serializer is supplied. The wire keys are `platform[platform]`, `platform[browser]`, and `platform[login]`, represented by an OpenAPI deepObject/explode parameter, not a JSON string.
- The `platform` query for #16344 remains a JSON string: +0x22 obtains the constructor result, +0x26/+0x29 unconditionally assigns nested `login` from explicit argument 2, +0x2f/+0x32 assigns `push_token` only when explicit argument 1 is truthy, and +0x57/+0x5c JSON.stringify encodes the object into `params.platform`. `query.fields` describes the pre-serialization object, not extra query parameters. Caller-derived nested values/types stay unknown; only push_token has proven conditional inclusion metadata. JSON.stringify can omit an undefined login value, so an unconditional assignment does not prove wire/server requiredness.
- The two URL components in #16391 are kept as generic `pathPart1`/`pathPart2`: its header has 3 params including implicit `this`, so there are exactly two explicit arguments (+0x22/+0x29), concatenated at +0x30 before URL-only GET +0x34. Their semantic names remain unresolved; there is no third explicit argument.

## Response handling

Responses are `unknown` because complete service response schemas are not established. The wrappers commonly unwrap `response.data`; #16351 and #16354 specifically return `response.data.left`. #12711 returns truthy `response.data` or an empty object and converts rejection to an empty object. #16308 and #16323 return Axios promises without a response-data unwrap. These client transformations are not server response completeness claims.

- RegisterUser selects #16318 at #16317 +0x26. #16318 (full lines 648856–648871) +0x03–+0x0b tests `response.status === 200`; +0x13/+0x18 returns response.data only then, otherwise +0x0f/+0x11 returns undefined. This is not evidence of server statuses or success/error schemas.
- Authorize #16398 constructs precisely `{socket_id: authorizeArgument1, channel_name: capturedAuthorizerArgument1.name}`: #16397 +0x02/+0x05 captures authorizer argument 1; #16398 +0x1d/+0x20 assigns socket_id, and +0x25–+0x31 reads the outer slot's name into channel_name. Authorize argument 2 is the callback captured at +0x02/+0x05, not a channel object. #16399 +0x13/+0x19 calls `callback(null, response.data)` and returns its result; #16400 +0x0e/+0x14 calls `callback(error, null)` and returns its result. Neither response.data nor undefined is established as the callback's return value.
