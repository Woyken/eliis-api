# Guardian batch: authentication traces

Static-only analysis of `Login` (#16308) and `Login2FA` (#16309), using `/data/data/com.termux/files/home/eliis-analysis/eliis.hasm` and existing `evidence/research/auth-common.json` / `evidence/request-model-enrichment.json`. No login requests, private account access, or account writes were made. Candidate fulfillment-body fields are optional/open client observations, not a complete server contract; rejection-only `message` reads are recorded separately as error observations.

## Password login → challenge → two-factor request

- Password login UI handler #13512 (original header line 543678; M1231 dependency 26=M1574) builds `{username,password}` at +0x87–+0x9a and dispatches `userLogin` at +0x9f. The action path is M1574 `userLogin` (#16244/#16245) → dependency 3=M1575 → AuthService installer #16306, which binds `login` to #16308 (line 648505). Existing request evidence already proves #16308 reconstructs exactly `{username,password,platform}` at lines 648631–648638; platform is `getPlatform()` plus nested `login:"password"` (#16308 +0x22–+0x2a; #16340 lines 649231–649258). **No new request fields** were found, so `requestCandidates` is empty.
- #16308 calls `auth.post('/api/auth/login', data)` and returns the raw Axios promise. The consumer #13510 receives that Axios result, reads `response.data.type` (lines 543554–543567), and, if truthy, navigates to `Login Two Factor Auth` with `{provider: response.data}` (lines 543645–543652). The entire body object is passed as `provider`; the app does not construct a server response object.
- The fulfillment continuation is now traced through the original Hermes function headers: #13512 registers #13513 with `.then` (543721–543723); #13513 (header line 543736, offset `0x004aed63`) creates generator bridge #13514 (543745–543749); #13514 (header line 543754, offset `0x004aed88`) creates continuation #13515 (543758–543760); #13515 (header line 543765, offset `0x004aed91`) invokes its captured callback with the fulfilled value (543772–543779); response processor #13511 (header line 543661, offset `0x003365b2`) applies the captured handler (543665–543673), reaching #13510. These are continuation edges only and do not change the observed body fields or their unknown/optional status.
- The 2FA screen #27139 (M2340, original line 1048081) stores `route.params.provider`. It reads `provider.type` to choose local email-vs-authenticator instructions (lines 1048186–1048200) and initializes local state from `provider.locked_out` (lines 1048133–1048141). These prove only the corresponding client reads and do not establish a server enum, lockout type, or semantics.
- Crucially, #27140 (line 1048334) reads `provider.identifier` and copies it to request field `login_identifier` (+0x2d–+0x37); it copies the entered code to `code` (+0x26–+0x29). The M2340 dependency index 6 is M1575, and #16306 binds `login2FA` to #16309. Thus the observed identifier is carried from the first login **response body** (`response.data.identifier`) through route param `provider.identifier` into the 2FA request; it is not read from a cookie, token store, or keychain. This finding is limited to this exact app flow.
- #16309 adds its own `platform` object (+0x22–+0x26) and POSTs the caller object with the default Axios client to `/api/auth/login-2fa` (+0x3f; lines 648644–648663). Existing request model records `code`, `login_identifier`, and nested `platform.platform`/`platform.browser`, while preserving arbitrary service input as open. No extra fields were added here.

## Result and failure branches

These are local branches, **not universal server status claims**. The challenge branch hands through the whole response body and does not prove which fields the server must provide.
- Password rejection handler #13517 conditionally reads `error.response.data.message` and displays it in an error toast (lines 543810–543844). ## Cookie/session boundary and global HTTP errors

- #5603 (lines 254019–254130) creates distinct `auth` and `default` Axios instances. The configured request-cookie interceptor is installed on `default` only (+0x169–+0x189); #16308 uses `auth`, while #16309 uses `default`. Therefore existing `auth:"none"` for password Login means no configured saved-cookie request interceptor on that client; it does not guarantee native cookie absence. Login2FA uses default-client behavior, which reads the saved credential and can set `headers.cookie` through #5612 (lines 254346–254391). Neither client configuration proves that the server requires the cookie.
- Important interceptor distinction: #5603 installs successful-response callbacks #5619/#5621 on the two clients, but installs rejection handler #5620 only on `default` and #5622 on `auth` (+0x19c–+0x1da). #5622 is only `Promise.reject(error)` (#5622 lines 254675–254684). Thus Login2FA can take the #5620 status handling path, but password Login's `auth` rejection does **not** take the global 401 cleanup path established below.
- The successful-response callback invokes the shared set-cookie helper (#5619/#5621 → #5615/#5617). #5617 reads only `headers['set-cookie'][0]`, parses `eliis_csrf`, serializes that cookie value, invokes native `clearAll`, then calls `saveAccessToken` (original lines 254472–254505). `CookieManagerModule.java` lines 133–149 implements native cookie removal. #6562 stores the supplied serialized value using keychain service `accessToken` (lines 288790–288804); #5612 later reads it for the default request-cookie path. This is a client-side credential capture/rotation/persistence effect driven by the first `set-cookie` array entry in a response **header**, not an API body field; no body credential is established. No keychain/native cookie value was accessed.
- Shared default-client error handler #5620 (original line 254553) reads Axios `error.response.status`, not an HTTP-body property. It compares status to 401 and calls configured `onUnauthorized` (+0x4b–+0x56, +0x91–+0xae); compares 412 and calls `onVersionInsufficient` (+0x64–+0x8f); and skips the version callback for 429 (+0x5a–+0x60), which continues through generic handling. Other branches may route `response.data.message` or `error.message` to `onMessage` depending on available fields (#5620 lines 254557–254650). These comparisons document client logic, **not** universal server statuses or an explicit expired-session detector.
- For the default-client 401 branch, #5593 first invokes an opaque environment callback and then calls `userStateCleanup` (#5592/#5593 lines 253763–253801). #16269/#16272 then dispatch `clearAccessToken`, disconnect, dispatch `RESET_STATE`, and purge the Redux persistor (lines 647592–647687). The `clearAccessToken` wrapper #6567/#6568 reaches #6570, which calls `resetGenericPassword` for keychain service `accessToken` (lines 288903–288977). This proves client credential/state cleanup for that configured default-client 401 path. The opaque callback's identity/effect is unresolved; the traced code contains no explicit `navigate`/`resetRoot` call, so no navigation reset is claimed. `RESET_STATE` alone is not evidence of a navigation action. The branch also does not prove that the server's 401 means session expiry, nor does it apply to Login's auth-client rejection branch.

## Candidate disposition

`auth.json` carries two response candidates and two endpoint capability records. Login fulfillment-body fields are `type`, `identifier`, and `locked_out`; Login2FA fulfillment-body fields are `status` and non-valid-branch `locked_at`. The rejection handlers separately read `error.response.data.message`; this is retained as an error-body observation, not part of either fulfillment response model. Every type/presence/domain remains unknown. Status codes and literal body comparisons are recorded only as local control flow. Request candidates are empty because current research/request-model evidence already contains the proven request fields and this tracing found no additional request construction.

Blockers remain: no live/server validation; no complete success/challenge/failure body; no server requiredness, auth requirement, response statuses, enum domains or `locked_at`/`locked_out` semantics; and no proven server meaning for the default client's 401 handling. The app does clear its saved `accessToken` keychain item and resets app state on that configured 401 path; that logic does not explicitly navigate/reset the root in the traced handler and is not installed for password Login's auth-client rejection. The 2FA identifier mapping is specific to the M1231 password-login → M2340 challenge screen chain, not a universal mapping.
