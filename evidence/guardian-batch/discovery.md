## Init-derived children: exact downstream reads and break

The causal chain is `GetUserData #16344 -> response.data #16345 -> init thunk #16201 -> body handler #16202 -> SET_USER_CHILDREN.data -> userReducer #25102 state.user.children -> DashboardScreen #34531/#34536 -> map callback #34568`. The DashboardScreen calls `.map` on the selected value, so `children` is modeled as an observed client collection with a partial object-item view. Callback `#34568` reads `item.id`, `item.name`, and `item.profile_picture`; it renders the latter two and compares the id to local active-child selection state. Child-row press callback `#34569` passes that init-derived `item.id` to the captured selection callback `#34563`.

The next observed screen chain is distinct: MyChildStack `#44019` accepts `route.params.childId`; MyChildInfoScreen `#44120` reads that route value and invokes GetChildProfile through `#44124`; ChildPlansScreens `#44258/#44264` likewise uses route childId for GetChildCourses. The inspected bytecode does **not** show the `#34563` selection callback's ID being placed into either screen stack's `route.params.childId`. That missing handoff is the precise causal break. Consequently, the init-derived child IDs and names are useful observed UI fields, but they do not establish that either downstream request is for that selected init child.

`kindergartens[*].id` and `organizations[*].id` are directly read by their init selection callbacks and compared with local selected IDs; these are client comparisons, not global stability guarantees. The child-list consumer above does not read `user.children[*].kindergarten_id`. MyChildInfoScreen's pre-request `myChild.child.kindergarten_id` is a separate state read, so this candidate does not back-attribute it to the init child list.

`guardians`, `children`, and `employees` remain separate root init values, dispatched to separate state slots. The additional guardian consumer is `state.user.guardians -> #34583.find -> #34584(candidate.kindergarten_id === selectedKindergartenId)`. This proves a client-side kindergarten comparison only. It reads no guardian item ID and makes no join to child items or the signed-in user. Do not substitute the staff-wide child roster (`#259..`) or the employees collection.

## Profile and active-course response boundary

In MyChildInfoScreen, `#44124` loads environment slot 5, which setup populates from selector `#44122`; it then loads route childId from slot 7 and literal false at lines 1800742-1800754. The bytecode defines `#44121` as returning whole `state.myChild.child`, `#44122` as returning its `kindergarten_id`, and `#44123` as returning `deleted_at` (1800687-1800728). Thus `#44124` passes the selected `kindergarten_id`, not the whole child object. Its false context selects `#25519`'s `SET_CHILD` branch. Separately, ChildInfoScreen caller `#44673/#44679` loads literal true at 1828051-1828052 and passes it as thunk argument 3 at 1828065, selecting `SET_MY_CHILD`. In that branch, response body → `#25519` → `#25496` stores the remainder under `myChild.child`, which `#44121` selects and `#44120` reads for `name`/`profile_picture`. This supports partial profile body observations without attributing them to the false-context #44124 invocation. Both screen/caller branches are client paths, not server authorization or guardian-role proof.

The callback parameter `r4` is the response body. It reads/dispatches `r4.active_courses`, may call `.find`, then directly deletes `active_courses` from `r4` at #25519 line 1000578. Only after that does it construct a separate `Object.assign` local state wrapper at 1000581-1000586, including the locally found `course` value. This is an in-memory client mutation of the callback object—not a server write—and neither the local `course` wrapper nor Redux wrapper becomes an HTTP field. The unknown active_courses container retains only the nested `.type` observation.

On the true-context branch only, `#25519` dispatches the response remainder as `SET_MY_CHILD`; `#25496` stores it under `myChild.child`. `MyChildInfoScreen #44120` reads `myChild.child.name` and `profile_picture`; selector `#44121` returns the whole child state. Selector `#44122` returns its `kindergarten_id`, and #44123 returns `deleted_at`. These support partial root `name` and `profile_picture` observations on that response-to-consumer path. The callback's newly created `course` property and the local state wrapper are not modeled as HTTP properties.

No active_courses item ID or course name is read by the profile callback, and no ID comparison joins those records to GetChildCourses. The profile candidate retains `active_courses` as unknown with the nested `.type` observation; it does not equate the local found course wrapper with course-list entries. The same-name root `name` read belongs to the child profile item, not to a course record.

## Courses response: UI trace and remaining limit

GetChildCourses `#25624/#25625` returns the body unchanged. The exact action `#25522/#25523` sends it as `SET_MY_CHILD_PLANS_COURSES.data`; reducer `#25496` stores it as `plansCourses`. Selector `#44259` returns that value; `#44274` reads each item's `name` and `id`, and #44275 uses the latter as local route param `courseId`. Separately, in the same screen effect `#44264` tests the response for null/nonzero length, reads `body[0].id`, and calls `getChildCoursePlanTypes`; service `#25626` places the third argument in `params.course_id` at 1003209-1003214. This establishes a response-derived ID use on a separate GET, not enrollment semantics, stable ID guarantees, or a mutation/write.

This UI establishes use as selectable course-like entries, not server enrollment semantics. There is no corresponding ID read from profile `active_courses`, no active/enrolled field read, and no stable-ID guarantee beyond reuse as the client route value. The childId/selected kindergarten arguments are visible at the screen call site, but the path from the init child-row selection to route.params.childId remains unproven.

## Permissions and role/view state

Permissions body is stored unchanged as `user.permissions`. The observed keys are `diary_access_course`, `diary_access_manager`, `applications_access_manage`, `surveys_access_index`, `surveys_access_questionnaires`, `surveys_access_polls`, `workschedule_access_index`, and `child_access_managerfields`; each selector gates on truthiness, not strict Boolean comparison. This is a partial inventory of client feature gates only, not server enforcement, field requiredness, Boolean types, role identity, or guardian-child authorization. Init `user.privacy_confirmed` separately drives a local privacy-state comparison, not an access gate. `employeeView=false` and EmployeeChildStack are client view modes, not server roles.

## Request/query, dates, pagination, effects

- `GetUserData`: one string-valued `platform` query built with `JSON.stringify`; nested fields describe its pre-serialization object, not additional query keys. `login` is assigned from argument 2; `push_token` is assigned only when argument 1 is truthy. No date/page input is sent. Init fulfillment dispatches state and performs selected-entity processing, including a client-triggered `getKindergartenLanguages` read; no write/seen mutation is established.
- `GetUserPermissions`: no query/body; `kindergartenId` is a path segment. No date or pagination semantics. Fulfillment replaces local permissions state; no optimistic fields are constructed in the success chain.
- `GetChildProfile`: no query/body/date/page parameters; two path segments at the service. Caller #44124 passes selector #44122's kindergarten_id value as argument 1 and false thunk context; keep separate from the true-context ChildInfoScreen caller. Fulfillment mutates only the in-memory callback body then constructs local state; no write/seen request is shown.
- `GetChildCourses`: no query/body/date/page parameters for this operation; two path segments. Its fulfillment is stored unchanged, then #44264 may trigger a distinct plan-types GET with response-derived `body[0].id` as `course_id`; this follow-up read is not a write/seen request.

No request additions are proposed; existing `evidence/research/auth-common.json` and `evidence/research/children-diary-files.json` already record these request shapes. Remaining blockers are the guardian-to-child join/authorization, the exact selection callback to route childId handoff, and a response-level active_courses ↔ courses ID match.
