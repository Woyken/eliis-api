## Guardian feed body and caller query

The service returns Axios `.data` unchanged. Its exact callback #25516 places that body unchanged on Redux `action.data` (full-disassembly lines 1000478–1000502); the separately captured `page` is an action-wrapper property. `dashboardReducer` #26862 reads `action.data.data` (lines 1039798–1039802) and `action.data.next_date` (1039808–1039810). Thus these are root properties of the HTTP body: `data` is the mapped collection and `next_date` is its sibling. This is **not** a `body.data.data` / `body.data.next_date` envelope. Child reducer #25496/#25497/#25498 independently maps the same raw `action.data.data` groups (999311–999324, 999679–999790), corroborating the boundary. For each `data[]` member, #26865 reads `date`, maps `diaries`, and checks `evaluations.length`; #26866/#25498 add `displayType` locally.

The feed UI passes the same diary entry through #34944 → #34941 to `ChildDiaryEntryItem` #34949. Its client reads establish partial fields under `data[].diaries[]`: `course`, `texts`, `status`, `meals`, `total_time`, `summaries`, `images`, `documents`, `feedback`, `likes`, and `id`. `status` is read through `color`/`icon`/`name`; `texts` is tested as `typeof object` and enumerated with `Object.keys`, which also admits arrays. No `Array.isArray` check or fixed dictionary guarantee is established, so the observed shape remains unknown/ambiguous between object and array, with no inferred keys or value types. `meals`, scalar-looking values, and `likes` remain unknown. `summaries`, `images`, `documents`, and `feedback` are mapped collections; summary and feedback items expose only a `comment` read, and feedback items additionally expose `owner` (not `owner.name`). Image/document item properties remain unobserved. All are partial client reads: no guaranteed presence, fixed nested shape, or complete server response follows.

The traced action caller constructs `params: { date }`. At #25515 lines 1000445–1000458, a falsy selected `diaryNextDate` branches to the formatter. For a truthy value, `JStrictNotEqual` at offset `0x59` jumps to `0x7b` when the captured page is not `1`, skipping the formatter and preserving the selected value. Otherwise (a falsy value on any page, or a truthy value on page `1`), the imported default formatter is called with no explicit argument; the `Call1` instruction uses an undefined receiver, not an undefined argument. Its result is then passed to `.format('YYYY-MM-DD')`. Either the copied cursor or formatter result is assigned to `params.date`; the formatter's no-argument result is not inferred. `page` is carried as client/action/reducer state, not added to the request params. There is no proven `perPage` field. The service itself forwards an arbitrary params argument unchanged, so this one caller does not establish the endpoint-wide query contract. Timezone, date inclusivity, and server interpretation are unresolved.

Do not infer unobserved entry properties such as `contentDate`, `created_at`, `published_at`, `updated_at`, title, description/HTML, generic `media`, attachment details, filetype, URL, filename, or thumbnails. Do not infer fixed `texts` dictionary keys, meal shape, image/document item fields, feedback owner subfields, or likes shape. The empty-state string “There are no published diary entries” is presentation copy, not a response field or server visibility guarantee. In particular, no guardian-visible field for publication, role, view permission, or other-child/class aggregation is proven.

`ChildDiaryScreen` module factory #44109 resolves the screen's dependencies; #44110 has an `employeeView=false` client branch: selectors #44111–#44114 read `state.myChild.child`, `diaryCurrentPage`, `diaryNextDate`, and `diary`, while the employee branch reads corresponding `state.child` values. Fetch closure #44115 reads and invokes the imported `getGuardianFeed` export; this is the same-named action creator #25514 (which returns thunk #25515), not an inference from ChildServices helper #25632's similar name. The MyChild reducer path #25496–#25498 maps the same raw `body.data` groups. This establishes a client UI/state branch only; `myChild`, `childId`, and `employeeView` are not proof of server-verified guardian authority, own-child authorization, or permission to see feedback from any other child. The separate employee/course `diary_access_course` gate is not guardian authorization evidence.

## Secondary diary endpoint

`GetGuardianDiary` builds a child `/diary` GET without query params, but only its service registration is referenced in the full disassembly search. No action, reducer, or UI body consumer is tied to it. Its candidate remains `kind: unknown` with no invented fields.

`GetDiaryData` builds `/api/kindergartens/{kindergartenId}/diary` with locally constructed `course` and `date` query keys. The primary action chooses fallbacks from employee and diary state. Callback #25783 reads the 15 root values retained in the candidate model; `statuses` is iterated and only `used_in_course` and `type` are read on status items. Fallback arrays and `{liked:false,users:[]}` are client-created, not response fields. The action's `resetFirst` is not part of Axios params. Another caller #43846 invokes `flushDiaryAutoSaves` before the GET and then only does modal cleanup; do not conflate possible autosave writes with GET behavior or perform them.

## Read effects and blockers

The GuardianFeed screen's refresh/load-more/focus/resume handlers trigger fetches. The traced successful feed callback only dispatches body and page state; no explicit mark-seen/read POST was found in this exact flow. That bounded observation is not proof that no notification/read operation exists elsewhere. `GetGuardianDiary` has no caller flow to assess. No server permissions, response statuses/media, date timezone rules, or complete response models are established. Do not recommend any of these as general guardian access until an exact guardian caller and its own-child/visibility conditions are proven.
