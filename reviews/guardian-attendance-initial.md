## Finding

### P1 — Two request candidates cannot be merged as currently shaped

The guardian-batch checker appends candidate query fields to each base research record (`scripts/check-guardian-batch.mjs:63–66`) before calling `validateRecord` (`:77`). The validator rejects duplicate query names and only permits query types `unknown`, scalar primitives, and the supported array forms (`scripts/generate.mjs:5–8, 33–53`).

- **#25650 / `date`:** the base `GetStatusLogs` record already has `query.date` (`evidence/research/children-diary-files.json:976–981`). Appending the candidate’s second `date` fails duplicate-field validation. If integration wants to promote the caller-proven formatted string, enrich/replace the existing field in place; do not append a second request field. The selected-day format and unresolved server semantics are already clearly captured in the candidate’s query/capability evidence.
- **#25652 / `form`:** the base record already has `query.form` (`children-diary-files.json:1016–1021`). The candidate both duplicates it and declares query `form` as `type: "object"`, which is not an accepted request/query type. Preserve the existing logical `form` query parameter as `type: "unknown"`; if the nested caller construction is retained, enrich that same field with a nested `user_id: unknown` observation. Do not add `encoding` or claim a serialized `form[user_id]`/`form.user_id` wire key without serializer evidence.

These are integration/representation defects, not evidence against either caller observation. `GetChildCalendar`’s new `start_date`/`end_date` fields do not duplicate existing named query fields in its base record.

## Other contract checks

- Candidate response models stay partial/open, use `unknown` where scalar types or raw item shapes are not proved, and avoid importing calendar UI-composed fields (`date`, `attendance`, `entry`, status labels, planned/actual values, arrival/pickup data) into raw `days[]`.
- The calendar permission discussion distinguishes the response’s opaque `access` value and local guardian edit gates from server authorization. Missing arrivals/logs are not treated as absence.
- Status history distinguishes `created_at` display conversion from attendance `start_time`/`end_time`; displayed names and `type`/`status` branches do not become actor identity or a transition dictionary.
- Read/reset/navigation state effects are kept separate from server writes. The reported GET flows do not claim a mutation; separate calendar POST/save paths are identified as such, and status history’s no-follow-up read/seen observation is scoped to the inspected flow.
- Capability `querySemantics` claims use established `true` and unresolved `false` dispositions consistently. No broader contract or semantic finding is required before integration beyond the request-candidate issue above.
