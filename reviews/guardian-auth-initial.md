# Initial xhigh candidate review — guardian auth

**Disposition: Hold for one response-trace completeness fix.** The auth and 2FA semantics in the candidate are otherwise evidence-backed; this review found no supported request or response claim that needs to be withdrawn.

Scope was limited to `evidence/guardian-batch/auth.json`, `evidence/guardian-batch/auth.md`, `evidence/guardian-batch/CONTRACT.md`, the repository `AGENTS.md`, the existing auth research/response records, and read-only Hermes source. No login/2FA request, private record access, or keychain/native-cookie value access was performed.

## Finding

### P2 — Add the omitted promise-continuation functions to the response traces

`auth.json` currently jumps from each request handler to its body consumer without recording the continuation functions that connect them. The source confirms the edges, but they should be present in the candidate trace so the evidence record itself carries the service → caller → response-consumer chain required by the contract.

- **Login:** candidate trace entries for `#13512` and `#13510` (`evidence/guardian-batch/auth.json:14–15`) skip the fulfillment continuation. `#13512` attaches `#13513` at Hermes lines 543721–543723; `#13513` constructs the async response handler and reaches `#13515` (543736–543765); `#13515` invokes the captured response callback (543772–543779), which forwards to the response processor `#13511` (543661–543673) and then `#13510` (543554 onward). Add the relevant bridge function IDs/lines to the Login trace.
- **Login2FA:** candidate trace entries for `#27140` and `#27143` (`auth.json:44–45`) omit the fulfillment bridge. `#27140` attaches `#27141` at lines 1048355–1048361; `#27141` creates `#27142` at 1048370–1048383; `#27142` creates the response processor `#27143` at 1048388–1048394. Add those bridge functions to the Login2FA trace.

This is a trace-coverage issue, not a counterexample to the body observations. The relevant original-source paths are present and establish the claims.

## Claims verified

- **Login request:** `#16308` uses the isolated `auth` client, constructs the outer `username`, `password`, and `platform` body, and returns the Axios promise unchanged (`eliis.hasm:648612–648639`). The password screen constructs `{username,password}` and dispatches the `userLogin` action (`#13512`, `543678–543723`); its module/action/service wiring is consistent with the candidate's M1231/M1574/M1575 trace. No additional request fields or query parameters are supported.
- **Challenge response and identifier:** the Login consumer reads `response.data.type`, branches on its truthiness, and passes that exact `response.data` value as route `provider` (`#13510`, `543554–543567`, `543645–543652`). The 2FA screen reads `provider.type` and `provider.locked_out` (`#27139`, `1048133–1048141`, `1048186–1048200`). Its submit handler copies `provider.identifier` to request key `login_identifier` and the entered code to `code` (`#27140`, `1048348–1048354`). The identifier is therefore a challenge-body value in this observed flow, not a cookie/keychain value; it is not a general mapping for other 2FA operations. Types, presence, and server meanings remain unknown.
- **Login2FA request/response:** the exact app handler builds `{code, login_identifier}` (`#27140`, `1048348–1048354`), and `#16309` adds `platform` and posts the forwarded payload through the default client to `/api/auth/login-2fa` (`648644–648663`). `#16310` returns `response.data` unchanged (`648673–648679`). The body-property comparison `result.status === "valid"` is at `#27143:1048407–1048409`; `locked_at` is read only on the **non-`valid`** branch and passed to local `invalidCodeHandler` (`1048410–1048423`). The handler does not inspect that argument (`#27156`, `1049116–1049144`). No type, enum, lockout meaning, or HTTP-status claim follows.
- **Transport status vs body:** Login's `response.status` comparisons to 200/202 are Axios transport/UI branches in `#13510:543572–543640`, not body fields or universal server statuses. Login2FA's body `status` is separate from Axios status. The candidate keeps both distinctions intact.
- **Rejections and `message`:** Login's `#13517` reads `error.response.data.message` only under response/data/message guards (`543810–543844`); Login2FA's `#27145` does likewise (`1048490–1048524`). These are rejection-body observations, not fulfillment fields. The candidate explicitly labels this branch in each `message` field's evidence and in the capability claims/limitations (`auth.json:24, 31, 53, 60, 72, 119`). That is sufficient for this evidence candidate. During integration, retain that branch scope: either keep `message` only as a non-normative error-body observation, or include it in an optional/open union of observed body paths with the rejection-only evidence preserved. Do not imply that successful Login/2FA bodies contain `message`.
- **Cookie boundary:** `#5603` installs the request-cookie interceptor on `default`, not `auth` (`254107–254113`), while installing the shared successful-response cookie handler on both clients and a rejection handler only on `default` (`254117–254128`). Thus `auth: "none"` for Login describes configured request-client behavior only; it does not prove absence of ambient native cookies or a server auth policy. The shared success handler examines `headers['set-cookie'][0]`, parses `eliis_csrf`, serializes that value, calls native `clearAll`, and then reaches `saveAccessToken` (`#5617`, `254472–254505`; persistence wrapper `#6562`, `288790–288804`). This is header-driven local credential handling, not a response-body field. The candidate correctly does not claim that the body supplies the token.
- **Default-client 401 cleanup:** `#5620` reads `error.response.status`, calls configured `onUnauthorized` for 401, and handles other status branches locally (`254553–254596`). The callback wiring reaches `userStateCleanup` (`#5592/#5593`, `253763–253801`); the cleanup thunk dispatches `clearAccessToken`, disconnects, dispatches `RESET_STATE`, and purges the persistor (`#16272`, `647634–647687`), while the clear action reaches `resetGenericPassword` for service `accessToken` (`#6570`, `288954–288977`). This applies to the default client only: the auth client's rejection handler is `#5622`, which simply rejects the promise (`254675–254684`). The candidate correctly leaves server 401/expiry semantics and explicit navigation reset unclaimed.
- **Unresolved scope:** no live login/2FA, server validation, private account access, credential-value inspection, or behavioral test was done. The stated blockers around requiredness, auth requirements, response completeness, status meanings, and lockout semantics are appropriately unresolved.

## Integration note

After adding the two continuation traces, the candidate is suitable for integration as partial, client-observed evidence. Keep every body field optional/unknown, retain the branch distinction for rejection `message`, and do not promote Axios statuses, UI literals, or local cleanup into server contract semantics.
